# 6. Commit Generated Module Federation Types

Date: 2026-10-19

## Status

Proposed

## Context

The host consumes types that federated remotes expose (extension-point data
types, exposed modules) through the `@mf/*` path alias, which resolves to
`frontend/@mf-types/`. Those files are generated by the Module Federation DTS
plugin when the host runs `pnpm run start:dev:mf` with the remotes running
locally (`MF_UPDATE_TYPES`, `frontend/config/moduleFederation.js`).

The generated types are committed (`@mf/modelRegistry`, `@mf/evalHub`). No CI
step regenerates them or checks for drift: `frontend/tsconfig.json` and lint
exclude the directory, and PR build validation skips it. So when a remote
changes an exposed type without regenerating, the host keeps compiling against
the old shape, and a consumer that needs the new type cannot import it.

## Decision

Generated remote types in `frontend/@mf-types/` are committed. A change to a
remote's exposed modules or extension-point types regenerates them with
`pnpm run start:dev:mf` (remotes running) and commits the result in the same
PR.

## Review rules

- A PR that adds or changes an exported type in a remote's
  `extension-points/` (or another exposed module) must include the matching
  regenerated files under `frontend/@mf-types/@mf/<remote>/`.
- Do not hand-edit files under `frontend/@mf-types/`; regenerate them.

## Consequences

**Positive:**
- Host and packages type-check against the remote's current contract.

**Negative:**
- Regeneration needs the remotes running locally.
- Without a CI drift check this relies on authors and review.
